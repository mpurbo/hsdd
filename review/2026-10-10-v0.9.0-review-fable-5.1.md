# HSDD v0.9.0 review

**Reviewer:** Claude Fable 5.1, cold read of `feat/v0.9.0` at `34b18de`
**Date:** 2026-10-10
**Subject:** `spec/hsdd-spec-v0_9.md`, the nine skills and their commands, `README.md`, `docs/users-guide.md`, `CHANGELOG.md`, `review/hsdd-v0_9-acceptance.md`, and the `hsdd-summary` scripts and tests
**Asked:** check that skipping the v0.8.0 release is handled consistently; find inconsistencies, gaps and defects across spec, implementation and user-facing documents; give an honest opinion on direction.

## 1. Verdict

**Do not tag v0.9.0 as the branch stands.** One claim in the spec is wrong in a way that misleads an upgrading user, and the acceptance record has no results.

The spec says v0.8.0's consolidation "ships for the first time in this release" and marks only chapters 6 and 11 as specified-not-shipped. In fact none of the v0.8 rules that amend the eight pre-existing skills were ever applied to those skills. The verification template has no Learnings or Metrics section, the contract template has no `compatibility` field, the node template has no `Team` or `Status` field, reconcile never checks executable validation, checkpoint knows nothing about backfill, sealing or the grandfather clause. About fourteen rule groups are in this state, and chapter 15's upgrade table presents them as live. The README and users guide repeat one of them (the grandfather marking) as a promise.

Everything v0.9 itself adds is in better shape: the phase context and derivatives are specified and implemented consistently, the reading-aid engine has 142 passing tests and behaves as the skill describes when run against the fixture tree, and the clean-room and vendoring rules hold. What is missing for v0.9's own scope is the cold-context acceptance run (A1 to C3, all `Result:` fields empty) and a set of smaller spec and documentation inconsistencies listed in section 3.

On direction: the core method is sound and the management layer is good for the problem it was built for. The project as a whole is over-extended relative to its evidence. The right move is not to abandon but to stop adding, shrink, and spend the next cycle producing the evidence the spec itself names as the v1.0 criterion. Section 5 argues this in full.

## 3. Findings

Severity: **Blocking** (must change before tagging), **Important** (a reader of the spec or guide will be misled or a path will fail), **Minor** (consistency and polish).

### 3.1 Blocking: the v0.8 skill amendments were never made, and the spec says they shipped

The v0.8.0 CHANGELOG entry and the v0.8 acceptance record (criterion 13) both state that no skill file was edited in v0.8 and that "the amendments to the existing eight follow in a separate cycle". That cycle never ran. The v0.9 branch changed `hsdd-config`, `hsdd-checkpoint`, the conventions template, and added `hsdd-summary`. Nothing else in `skills/` differs from `main` except through those files.

The v0.9 spec then says, in its header, that v0.8.0's consolidation "ships for the first time in this release", and chapter 15's first table lists each v0.8 change with its effect on an existing project as though the skills deliver it. Only chapters 6 and 11 carry a "specified, not shipped" line.

A side effect worth naming: the new `hsdd-summary` extractor parses `Status: retired` and `Adopted:` fields that no authoring skill emits. The reading aid is ahead of the skills it reads.

**Options.**

1. **Wording only.** Add a "specified, not shipped" marker to each row above, or one table in chapter 15 listing the rules this document states that no skill implements yet, and correct the header sentence and the users guide paragraph. One commit, no skill touched, acceptance runs against the skills as they are. The spec stays honest; the gap stays open.
2. **Template-level amendments now.** The additive ones are prose edits to templates: Learnings and Metrics sections in the verification template, the four frontmatter keys in the contract template, three optional fields in the node template, an ordering-policy line in conventions. These change no skill behavior, only what a fresh artifact carries. The behavioral ones (reconcile's validation assertion, backfill, sealing, grandfather) stay deferred to v0.10.0 with adopt and intake.
3. **Full amendments before tagging.** Everything in the table. Delays the release by a cycle and puts the acceptance run on skills that just changed.

Recommended: option 1 for v0.9.0, option 2 as the first task of v0.9.1 after the acceptance run has passed on unchanged skills. Option 3 contradicts the owner's own practice of accepting before changing proven paths.

### 3.6 What holds up

- **Skipping the v0.8.0 release** is handled consistently in the three places that matter: the spec header, chapter 15 ("a project on 0.7.1 upgrades straight to v0.9.0 and takes both tables"), and the CHANGELOG's Unreleased note. The `spec/hsdd-spec-v0_8.md` file stays as history and nothing links to it as a reading path. Chapters 6 and 11 carry the specified-not-shipped line and the README and guide no longer describe them. The only gap is the one in 3.1: the same honesty was not extended to the v0.8 rules that touch the eight existing skills.
- **The phase context design** is consistent across spec §9.7 to §9.9, `hsdd-config`, the conventions template, the command and the users guide: same file names, same stamp, same five rules, same equality check, same `--method` override. The users guide's worked `config.yaml` block matches the skill's template section for section.
- **The reading-aid engine** does what its chapter says. The CSP is hash-based with `default-src 'none'`, the page inlines everything, `render` refuses targets outside `hsdd/summary/` after resolving symlinks, refuses a model from another project or from changed sources, and `check` always exits 0. The prose store is per page, so writing checkpoint prose does not stale the plan page. The fixture has the field drift the design asked for (bare field block, named-but-unwritten contract, provisional contract, undrained section, contingent phase, retired node, adopted node, same-date ties, misnamed files).
- **Provenance** is honest: every v0.8 and v0.9 row in §18.1 is `reasoned-only`, and the chapter's preamble says so.
- **Scripting boundary** is respected: scripts only in the new skill, `hsdd-checkpoint` reaches them behind the `hsdd/summary/` gate, `hsdd-config` stays prose.

## 5. Direction

The question was whether the direction is sound, good, just okay, or whether to abandon and pivot. Honest answer: **the core is sound, the management layer is good, the surface around them is over-extended, and the project's real risk is that it has become a specification effort rather than a validated method.** Not abandon. Stop adding, shrink, validate. Reasoning follows, in the order a skeptic would raise it.

### 5.1 Separate the three things HSDD bundles

1. **A decomposition and contract discipline** for agentic delivery across several owners: ownership-first axis, contracts as the only cross-node knowledge, phases sized to one human review sitting, tiered review, evidence-based done. Chapters 2 to 4 and 7 to 10.
2. **A management layer** for a lead who runs a weekly sync over several lanes: the evidence pass, cite-never-define, the findings-to-plan loop, milestone gates. Chapter 12, with chapter 13 as its reading surface.
3. **A context-window workaround.** The spec's opening paragraph: the spec becomes a monolith, every session re-reads everything, tokens explode. The isolation and token claims of §16.1.

These age differently, and the opinion is different for each.

### 5.2 The context-window rationale is the part being eroded

This is the part the question is really about. Native harness features now do a large share of what (3) was for: subagents with their own context windows, agent teams with a lead and a shared task list, compaction, memory, worktrees and plan mode built into the harness, and models with context windows an order of magnitude larger than when HSDD started. The literature now names "harness engineering" as its own discipline with context and memory as one of its layers. [1][2][3]

The spec already concedes the ground: isolation is "probabilistic, not enforced" and HSDD "does not reduce the total" token cost (§16.1). What is left of (3) is attention shaping, which a subagent per phase gives you for free. If HSDD's pitch stays (3), abandoning would be the right call within a year, because the opening sentence of §1.1 will read as a description of 2025.

But HSDD's own invariant is not (3). §1.3 and §7.2 say it plainly: the unit is the human review sitting, and the ~5-hour window is calibration, not definition. That rationale survives every model improvement, because the human reviewer does not get a bigger context window. The README, however, leads with (3) and only reaches the review sitting in its fourth bullet. The fix is a repositioning, not a pivot: HSDD is a method for keeping human review the pacing unit when agents produce faster than people can read, across more than one owner. That is still a real problem, and it gets worse as models improve, not better.

### 5.3 The decomposition discipline is sound and differentiated, but under-evidenced

The comparable tools in 2026 (Spec Kit, Kiro, OpenSpec, Tessl) all run one spec through one plan to one task list. [4][5] None does multi-level decomposition, an ownership-first axis, first-class versioned contracts with typed edges, or review tiers. That is HSDD's genuine contribution, and it is an architecture and management idea, not a prompting trick, which is why it is durable.

OpenSpec itself is healthy (v1.12.0 in September 2026, about 60k stars), so the dependency is not a risk, and v0.9 making it one of two methods was the right hedge. [6][7]

The weakness is evidence. The field record is: one monorepo test at v0.5 (14 phases, two nodes), one adversarial campaign at v0.6, one acceptance run at v0.7, and a prototype run at v0.9. Chapter 17 names the case study with a baseline as the v1.0 criterion and says FT-2 "lacks only the baseline and the write-up". That sentence has been true for four releases. Meanwhile the spec grew from a delta series to 2,630 lines, the skills to about 2,400 lines of prose, and v0.9 added 5,600 lines of JavaScript. Three of the last four releases are `reasoned-only` by the spec's own provenance column. Specification velocity has outpaced validation velocity by a wide margin, and that is the classic failure mode of a methodology: it becomes a document people admire and nobody runs.

### 5.4 The management layer is good, and the reading aids are the part to question

Chapter 12 was driven by a real checkpoint run on a real project and is the most field-tested of the recent material. For the owner's situation (a lead, several developers, a weekly sync, decisions that must be carried to the team rather than made at a keyboard) it is the highest-value part of HSDD and it is not something Spec Kit or Kiro offer.

Chapter 13 is well built. It is also the most product-like and least method-like thing in the repository: a UI over the management documents, with a vendored layout library, a CSP, three audiences and keyboard shortcuts. It costs the most per unit of methodological insight, it copies 49 KB of vendored JavaScript plus about 2,800 lines of scripts into every project's governance tree (and, under the profile, into the spec repo that every implementation repo mounts), and its "byte-identical to this skill's scripts" gate means every engine fix is a manual re-copy into every project. That is maintainable for one or two projects. It is not what a methodology needs to prove itself.

The more interesting thing chapter 13 did is reintroduce mechanization. The extractor is a parser of the HSDD formats. Its `unparsed[]` output is a lint of the tree: it found the planted format defects in the fixture, and it will find them in field trees. That is the vNext CLI's `lint` command, arrived by a side door, and it works. The decision to decline the CLI was risk-based (do not change how proven skills execute), not a rejection of mechanical checks, and this parser changes no skill. Running `extract` over every field tree and counting unparsed items is a cheap, model-independent conformance metric for the skills, which is exactly what prose-only skills lack.

### 5.5 Prose-only skills are the fragility that harness advances actually expose

The anti-rationalization tables in nine skills are tuned to how 2025 and 2026 models rationalize. Each model generation reads instructions differently, each harness redefines what a skill is, and the 0.6.0 pressure campaign has not been repeated since. Structural anchors (§1.4) were the right instinct, but most anchors are still checklist items in prose. The parser in 5.4 is the first anchor that a model cannot talk its way past. Investing there, and not in more prose rules, is the part of "harness engineering" that applies to HSDD directly.

### 5.6 Options

| Option | What it means | Trade-off |
|---|---|---|
| A. Continue as is | v0.10.0 ships adopt and intake, the eight amendments, then more chapters | Lowest disruption. Highest chance the case study never happens and the method stays `reasoned-only`. |
| B. Freeze and validate | v0.9.0 is the last feature release for a while. v0.10.0 is the case study: FT-2 or the field project, with the monolithic-spec baseline chapter 17 asks for. Adopt and intake ship only when a brownfield project needs them. | Costs a cycle of visible feature work. Produces the one artifact that makes the method defensible, and tells you which rules to cut. |
| C. Shrink the surface | Split the spec into a field-tested core (roughly chapters 1 to 4, 7 to 10, 12, 14; about 1,200 lines) and a proposals document for chapters 6, 11, 13 and the untested parts of 15. Four or five skills remain in the core. | Honest about provenance by structure rather than by a column. Readers of the core get what works. Some careful writing in 6 and 11 (the "a PRD is never a root" rule above all) belongs in the core as a rule even without a skill. |
| D. Ride the harness | Drop the OpenSpec coupling from the core (v0.9 already made it one of two methods), map one node to one agent-team lane and one phase to one subagent run, keep contracts, tiers, the checkpoint and the conventions file. | Smallest durable surface and the best fit with where harnesses are going. Ties HSDD to one harness's feature set, which is the kind of coupling the method avoided with OpenSpec. |
| E. Abandon | Stop. Keep the ideas as a practice note. | Justified only if the owner's projects stop needing more than one owner and human-paced review. For the scale of the owner's organization that is unlikely, and the decomposition discipline has no equivalent in the current tools. |

Recommended: **B, with C applied to the spec and the first step of D taken** (reposition the pitch around the review sitting and treat OpenSpec and superpowers as interchangeable execution methods, which v0.9 already did). Concretely for v0.10.0: no new chapters, the eight template-level amendments from 3.1 option 2, the extractor run as a conformance check across the field trees, and the case study with a baseline. Adopt and intake wait for a brownfield project that asks for them.

### 5.7 Grading

- Decomposition and contract discipline (chapters 2 to 4, 7 to 10): **good**. Field-tested, differentiated, durable.
- Management layer (chapter 12): **good** for a lead running a multi-lane project, and the part most worth keeping near the owner's daily work.
- Phase context and coding methods (chapter 9): **sound**, consistent across spec and skill, unproven until the acceptance run.
- Reading aids (chapter 13): **okay**. Well built, questionable return, and its parser is worth more as a lint than as a renderer.
- Brownfield and intake (chapters 6 and 11): **unproven**. One strong rule (§11.1) that deserves to live in the core; the rest should wait for a project.
- The whole: **okay, trending toward over-specification; sound if the next cycle produces evidence instead of rules.**
